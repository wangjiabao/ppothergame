# 索引依据与完整数据库读写清单

来源是两份项目当前代码，不是旧库SHOW INDEX。新增63个普通索引已内置01/00/08；10用于给已有表补索引。原有user.address普通索引按用户要求替换为唯一索引，当前共93个二级索引（91个普通、2个唯一键：user.address及random_seeds.scene），另有38个主键。user.address唯一约束来自用户明确要求；config.key_name/level等未加唯一约束。

## 设计依据与边界

- 等值条件放在范围条件前；按用户/类型/状态组合的常用路径建复合索引。
- InnoDB二级索引含主键id，因此单等值前缀后的id正序/倒序通常不必重复声明id。多值IN、非等值前缀及另一列排序不保证免filesort。
- 原idx_user_id保留：用户范围内按id分页与按created_at/状态过滤是不同路径；为不自动删除原有索引，本次只新增。存在左前缀重叠，最终可按真实EXPLAIN和使用频率精简。
- 只有主键id定位的更新不额外给每个余额/状态字段建复合索引；配置id更新已由主键支持。
- 小目录表只给实际按level/prop_type定位的字段普通索引，其他主键/全表读取由原结构支持。
- 没有真实数据库数据量、状态分布、EXPLAIN或压测，本次是有代码证据的初始索引设计，不是性能验收。

[MySQL复合索引官方说明](https://dev.mysql.com/doc/refman/8.0/en/multiple-column-indexes.html)、[范围优化官方说明](https://dev.mysql.com/doc/refman/8.0/en/range-optimization.html)。

## 有数据后优先验证的取舍

| 查询 | 当前选择 | 尚需真实数据判断 |
|---|---|---|
| 五分钟土地计数事件 | 原恢复文件的`(status,limit_date,user_id)`保留，作为覆盖索引 | `status<=4`和`limit_date>当前时间`都是范围，不能同时用两列界定连续扫描区间；过期土地很多时limit_date放前可能更好。当前无法证明哪个顺序最佳；未盲目再加一份倒序组合 |
| 成熟作物列表 | `(status,one,two,over_time,sub_time)` | sub_time与over_time都是范围时，后者/前者只能选一者主导范围；本次优先结束时间，也对应排序。计数sub_time=0的选择性未知 |
| 用户库存status IN(...)且ORDER BY id | 用户/状态过滤索引及原user_id索引并存 | 状态IN有多个取值时可能仍排序，MySQL会按成本选过滤或排序路径 |
| 长推荐链LIKE prefix% | recommend_code(191)普通前缀索引 | 191字符以后剩余过滤；更长链或共同前缀多时收益有限；不能同时保证id倒序无排序 |
| 后台用户余额/土地数排行榜 | amount_usdt与land_count两个独立索引 | 两种排序来自if/else互斥分支，不能误建一个(amount_usdt,land_count)来替代；land_count每5分钟被事件更新增加维护成本 |
| sum/count时间统计 | 用户/币种/原因等值后接created_at/updated_at | 没有把所有SUM金额都塞进覆盖索引，避免写入代价膨胀；是否覆盖需真实负载再判断 |
